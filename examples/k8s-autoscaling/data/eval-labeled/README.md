# Committed held-out sets

These files are the held-out data the report scores. They are committed rather
than generated per run, so every account measures the same thing.

- `triage-heldout.jsonl`: 43 human-labeled messages, `{"input", "output", "id"}`.
  Read by `data.evaluation.labeled` in `triage/expert.yaml`. They carry origin
  `real`, and the report scores them separately from the generated set.
- `retriever-heldout.jsonl`: 42 (question, document) pairs,
  `{"query", "positive", "source", "origin"}`. Generated by the frontier model
  from the 14 documents in `data/eval-queries/` in one workshop account on
  2026-11-18, then committed, the way the triage training data was made. Read
  by `data.evaluation.labeled` in `retriever/expert.yaml` with
  `evaluation.pairs: 0`, so these pairs are the whole held-out set. They keep
  origin `synthetic`, because a model wrote the questions.

`positive` holds the exact text of a document chunk. The trainer locates a
pair's document in the retrieval corpus by that text, so editing a document in
`data/eval-queries/` breaks the pairs that point at it. The data pipeline
counts the pairs it cannot match and fails the stage above 5 per cent of them.

The count is in pairs. Each of the 14 documents answers three of the 42 pairs,
so editing one document leaves 3 pairs unmatched, which is 7.1 per cent and
fails the stage. Regenerate `retriever-heldout.jsonl` when you edit those
documents. A smaller share, one or two pairs, is reported as a warning and the
run goes on.
